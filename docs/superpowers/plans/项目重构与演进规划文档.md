## 模块一：邮件内容智能提取 (MIME 解析与清洗)
**目标**：解决 Token 浪费问题，精准提取正文，剔除签名、HTML 和附件。

### ?? 代码示例：递归解析 MIME 树
在 `background.js` 或独立的 `mime-parser.js` 中实现：

```javascript
/**
 * 递归提取邮件纯文本正文
 * @param {object} part - browser.messages.getFull() 返回的 MIME part
 * @returns {string} 纯文本内容
 */
function extractPlainText(part) {
  if (!part) return "";

  // 1. 优先寻找 text/plain
  if (part.contentType === "text/plain" && part.body) {
    return decodeBody(part.body, part.encoding);
  }

  // 2. 如果没有纯文本，退而求其次寻找 text/html 并清洗
  if (part.contentType === "text/html" && part.body) {
    const html = decodeBody(part.body, part.encoding);
    return stripHtmlTags(html);
  }

  // 3. 递归遍历子节点 (multipart/alternative, multipart/mixed 等)
  if (part.parts && part.parts.length > 0) {
    // 优先找 plain，找不到再找 html
    let plainText = "";
    let htmlText = "";
    for (const subPart of part.parts) {
      const result = extractPlainText(subPart);
      if (subPart.contentType === "text/plain") plainText += result;
      else if (subPart.contentType === "text/html") htmlText += result;
    }
    return plainText || htmlText;
  }
  return "";
}

// 辅助：简单的 HTML 标签剥离与签名截断
function stripHtmlTags(html) {
  // 移除 <style> 和 <script> 块
  let text = html.replace(/<(style|script)[^>]*>[\s\S]*?<\/\1>/gi, "");
  // 替换 <br> 和 <p> 为换行符
  text = text.replace(/<br\s*\/?>/gi, "\n").replace(/<\/p>/gi, "\n");
  // 移除所有剩余标签
  text = text.replace(/<[^>]+>/g, "");
  // 解码 HTML 实体
  text = text.replace(/&nbsp;/g, " ").replace(/&amp;/g, "&").replace(/&lt;/g, "<").replace(/&gt;/g, ">");
  
  // ?? 核心优化：截断历史引用和签名 (启发式规则)
  const signatureMarkers = ["-- ", "Sent from my iPhone", "Get Outlook for", "________________________________"];
  for (const marker of signatureMarkers) {
    const idx = text.indexOf(marker);
    if (idx > -1) text = text.substring(0, idx);
  }
  
  return text.trim().substring(0, 1500); // 限制最大 Token 长度
}
```

### ?? 易错点 (Gotchas)
1. **Base64 附件陷阱**：`multipart/mixed` 中可能包含 Base64 编码的图片或 PDF。如果不判断 `contentType` 直接读取 `body`，会把几万字符的乱码喂给 AI，瞬间耗尽 Token 并导致 API 报错。
2. **`multipart/alternative` 重复读取**：这种类型通常同时包含 `text/plain` 和 `text/html` 两个版本。**千万不要把两个版本拼接起来**，必须优先取 `plain`，取不到才取 `html`。
3. **编码问题**：Thunderbird 返回的 `body` 可能是 Base64 或 Quoted-Printable 编码的，必须使用 `atob()` 或专门的库进行解码，否则 AI 看到的是乱码。

## 模块二：动态右键菜单与热更新
**目标**：消灭“修改标签需重启 Thunderbird”的反人类设定。

### ?? 代码示例：监听 Storage 动态重建菜单
在 `background.js` 中：

// 初始化菜单
async function buildContextMenu() {
  await browser.menus.removeAll(); // ?? 必须先清空，防止 ID 冲突

  });

  labels.forEach(label => {

browser.storage.onChanged.addListener((changes, area) => {
  if (area === "local" && changes.labels) {
    console.log("Labels updated, rebuilding context menu...");
    buildContextMenu();
  }

// 扩展启动时初始化
browser.runtime.onStartup.addListener(buildContextMenu);
browser.runtime.onInstalled.addListener(buildContextMenu);
```

### ?? 易错点 (Gotchas)
1. **菜单 ID 冲突**：`browser.menus.create` 的 `id` 必须是全局唯一的。如果用户删除了一个标签又新建了同名标签，或者在循环中未 `await removeAll()` 就开始 `create`，会抛出 `Cannot create item with duplicate id` 错误，导致整个菜单崩溃。
2. **上下文 (`contexts`) 缺失**：Thunderbird 的菜单系统非常严格。如果不写 `contexts: ["message_list"]`，菜单可能只在网页内容或附件上右键时才显示，在邮件列表右键时不显示。

## 模块三：LLM 结构化输出与本地模糊匹配兜底
**目标**：解决 AI “幻觉”导致的文件夹匹配失败问题。

### ?? 代码示例：强制 JSON 与 Levenshtein 模糊匹配
```javascript
// 1. 计算编辑距离 (Levenshtein Distance)
function levenshtein(a, b) {
  const matrix = Array.from({ length: a.length + 1 }, (_, i) => 
    Array.from({ length: b.length + 1 }, (_, j) => (i === 0 ? j : j === 0 ? i : 0))
  );
  for (let i = 1; i <= a.length; i++) {
    for (let j = 1; j <= b.length; j++) {
      const cost = a[i - 1] === b[j - 1] ? 0 : 1;
      matrix[i][j] = Math.min(
        matrix[i - 1][j] + 1,
        matrix[i][j - 1] + 1,
        matrix[i - 1][j - 1] + cost
      );
    }
  }
  return matrix[a.length][b.length];
}

// 2. 解析 AI 响应并进行模糊匹配
function resolveDestinationFolder(aiResponse, userLabels) {
  let predictedLabel = "";
  
  // ?? 易错点：AI 经常不遵守纯 JSON 规则，会用 ```json 包裹，必须正则提取
  const jsonMatch = aiResponse.match(/\{[\s\S]*?\}/);
  if (jsonMatch) {
    try {
      const parsed = JSON.parse(jsonMatch[0]);
      predictedLabel = parsed.category || parsed.label || "";
    } catch (e) {
      predictedLabel = aiResponse.trim(); // 降级为纯文本匹配
    }
  } else {
    predictedLabel = aiResponse.trim();
  }

  // 精确匹配 (大小写不敏感)
  const exactMatch = userLabels.find(l => l.toLowerCase() === predictedLabel.toLowerCase());
  if (exactMatch) return exactMatch;

  // ?? 核心优化：模糊匹配兜底
  let bestMatch = null;
  let minDistance = Infinity;
  
  for (const label of userLabels) {
    const distance = levenshtein(predictedLabel.toLowerCase(), label.toLowerCase());
    if (distance < minDistance) {
      minDistance = distance;
      bestMatch = label;
    }
  }
  
  // 如果编辑距离小于阈值 (例如标签长度的 30%)，则认为匹配成功
  if (bestMatch && minDistance <= Math.max(2, bestMatch.length * 0.3)) {
    console.warn(`[AutoSort+] Fuzzy matched "${predictedLabel}" to "${bestMatch}"`);
    return bestMatch;
  }
  
  return null; // 匹配失败，交由人工处理
}
```

### ?? 易错点 (Gotchas)
1. **JSON 解析崩溃**：永远不要相信 LLM 会 100% 输出合法的纯 JSON。它可能会输出 `Here is the result: {"category": "Work"}`。必须用正则 `/\{[\s\S]*?\}/` 提取大括号内的内容再 `JSON.parse`。
2. **移动目标不存在**：即使用模糊匹配找到了标签，Thunderbird 的 `browser.messages.move` 需要的是**文件夹对象 (MailFolder)** 或完整的**文件夹路径 (Path)**，而不是简单的字符串名字。必须先通过 `browser.mailAccounts.list()` 遍历构建出准确的 `folderId` 或 `path`。

## 模块四：带并发控制与退避重试的异步任务队列
**目标**：解决批量处理 50 封邮件时触发 API 429 限流或导致 Thunderbird 卡死的问题。

### ?? 代码示例：健壮的任务队列
```javascript
class TaskQueue {
  constructor(concurrency = 3) {
    this.concurrency = concurrency;
    this.running = 0;
    this.queue = [];
  }

  add(task) {
    return new Promise((resolve, reject) => {
      this.queue.push({ task, resolve, reject });
      this.next();
    });
  }

  async next() {
    if (this.running >= this.concurrency || this.queue.length === 0) return;
    
    this.running++;
    const { task, resolve, reject } = this.queue.shift();

    try {
      const result = await this.executeWithRetry(task);
      resolve(result);
    } catch (err) {
      reject(err);
    } finally {
      this.running--;
      this.next();
    }
  }

  // ?? 核心优化：指数退避重试机制
  async executeWithRetry(task, retries = 3, baseDelay = 2000) {
    for (let i = 0; i < retries; i++) {
      try {
        return await task();
      } catch (error) {
        // 捕获 API 429 Rate Limit 错误
        if (error.status === 429 || error.message.includes("429") || error.message.includes("RATE_LIMIT")) {
          const delay = baseDelay * Math.pow(2, i) + Math.random() * 1000;
          console.warn(`[AutoSort+] Rate limited. Retrying in ${delay}ms...`);
          await new Promise(res => setTimeout(res, delay));
          
          // ?? 如果是 Gemini，这里可以触发 Key 轮换逻辑
          if (i === retries - 1) throw new Error("Max retries reached & all keys exhausted.");
        } else {
          throw error; // 非限流错误直接抛出
        }
      }
    }
  }
}

// 使用示例
const queue = new TaskQueue(3); // 最多同时处理 3 封邮件

selectedMessages.forEach(msg => {
  queue.add(async () => {
    const content = await extractPlainText(await browser.messages.getFull(msg.id));
    const aiResult = await callLLMAPI(content);
    const folder = resolveDestinationFolder(aiResult, userLabels);
    if (folder) await browser.messages.move([msg.id], folder);
  }).catch(err => console.error(`Failed to sort ${msg.subject}`, err));
});
```

### ?? 易错点 (Gotchas)
1. **Thunderbird 本地数据库锁**：`browser.messages.move` 是写操作。如果并发数设置过高（如 > 5），Thunderbird 底层的 SQLite 数据库可能会报 `Database is locked` 错误，导致邮件移动失败甚至索引损坏。**建议并发数严格控制在 2-3**。
2. **`setTimeout` 在 V3 中的失效**：如果你未来迁移到 Manifest V3，Service Worker 会在空闲 30 秒后被休眠。如果 `setTimeout` 的延迟时间较长，Worker 休眠后定时器会被直接抹除。**必须使用 `chrome.alarms` API 替代长延时**。

## 模块五：Manifest V3 迁移核心预警 (生死攸关)
知识库显示项目目前使用 `Manifest v2`。Mozilla 正在强推 V3，**不迁移将无法上架 AMO 商店，甚至在未来版本的 Thunderbird 中直接失效**。

### ?? V3 迁移三大“天坑”
1. **Background Page 变成 Service Worker**
   - **V2**：`background.js` 运行在一个隐藏的 DOM 页面中，可以使用 `document`、`window`、`localStorage`。
   - **V3**：变成纯 JS 环境的 Service Worker。**没有 DOM！没有 `window`！没有 `localStorage`！**
   - **对策**：所有 DOM 解析（如前文的 `stripHtmlTags`）必须改用纯正则，或引入 `DOMParser` 的 Polyfill；存储必须全部改用 `browser.storage.local`。
2. **状态丢失问题**
   - **V3**：Service Worker 会在无事件触发时**随时被杀死**。内存中的变量（如 `let dailyCount = 0`）会瞬间清零。
   - **对策**：任何需要持久化的状态（如 Rate Limit 计数器、任务队列状态）**必须**在每次变更后立即写入 `browser.storage.session` (V3 新增) 或 `storage.local`。
3. **XMLHttpRequest 被废弃**
   - **V3**：Service Worker 中**禁止使用 `XHR`**。
   - **对策**：调用 LLM API 必须全部使用原生的 `fetch()` API。
